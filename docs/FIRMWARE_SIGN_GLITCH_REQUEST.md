# 로드셀 펌웨어 수정 요청 — RQIW 응답 부호 미전송 (기본 '+' + 순회형 '-' 아티팩트)

> 관련 이슈: CHAI-Student/CRK-IO-BOARD#1 (부호 왕복 플리커).
> 원시 캡처 데이터: issue #1 코멘트 첨부 `flicker.jsonl` (664프레임, 양수 적재)
> 및 `after_fix2.jsonl` (664프레임, 음수 영역 실험).

## 1. 요약

로드셀 무게 조회(`RQIW`) 응답에서 **참 부호가 전송되지 않고 있습니다.**
두 조건의 캡처를 대조한 결과:

| 참값 | 보고 부호 | 비율 |
|---|---|---|
| 양수 (적재 상태) | `+` (정답) / `-` (오답) | 88% / 12% |
| **음수** (500g 영점 후 제거) | `+` (오답) / `-` (정답) | **89% / 11%** |

참값의 부호와 무관하게 보고 부호 분포가 동일합니다. 즉 펌웨어는 기본적으로
`+`를 출력하고, 프레임당 1~2개(인접) 채널에 **스캔 순서대로 순회하는 `-`
아티팩트**가 실리는 것이며, 이 `-`는 참 부호와 상관이 없습니다. 크기(절대값)는
두 조건 모두 정확히 보존됩니다. 결론적으로 **부호 정보가 와이어에 실리지 않는
상태**이며, 디지털 셀 응답의 X4 바이트 bit7(음수 플래그)을 실제로 판독해 크기와
동일 스냅샷에서 원자적으로 조합·전달하도록 수정을 요청합니다.

## 2. 관측 데이터 (실기)

### 2.1 양수 적재 상태 (`flicker.jsonl`)

수집 조건: `GET /loadcells` 폴링 ~90ms 간격, 60초, 664프레임, 전 채널 적재
상태(24~962g). 원시 프레임 발췌:

```text
frame 1: ch6만 음수   ["+00962","+00522","+00520","+00519","+00129","+00052","-00696","+00080","+00084","+00552"]
frame 2: ch7만 음수   ["+00962","+00522","+00520","+00519","+00129","+00052","+00696","-00080","+00084","+00552"]
frame 3: ch8·9만 음수 ["+00962","+00522","+00520","+00519","+00129","+00052","+00696","+00080","-00084","-00552"]
frame 4: ch0만 음수   ["-00962","+00522","+00520","+00519","+00129","+00052","+00696","+00080","+00084","+00552"]
```

정량 분석 결과:

| 항목 | 측정값 |
| --- | --- |
| 프레임당 `-` 채널 수 | 0개: 101, 1개: 365, 2개: 181, 3개: 16 프레임 |
| `-` 위치 이동 | 관측 간 +1칸이 229회로 압도적 (+3은 폴링이 내부 스캔을 건너뛴 것) |
| 2채널 `-` 프레임 | 181개 중 180개가 **인접 채널 쌍** |
| `-` 값의 크기 | 직전 정상값 대비 차이 **median 0.0g** (크기 완전 보존) |
| `-` 지속 | 782회 중 781회가 **정확히 1프레임** |
| 채널별 `-` 비율 | 전 채널 11.3~12.0%로 균일 |

### 2.2 음수 영역 결정 실험 (`after_fix2.jsonl`)

500g 추를 올린 상태에서 영점(`MC LZ`) 후 추를 제거하여 참값을 −500g으로
만든 상태(ch5), 동일하게 −131g 상태(ch8)로 60초 수집:

| 채널 | 참값 | 보고값 | `+` 비율 (duty) |
| --- | --- | --- | --- |
| ch5 | −500 | ±499~505 | **0.89** |
| ch8 | −131 | ±131 | **0.94** |

참값이 음수인데 보고는 89~94%가 `+`입니다. `-`가 실리는 비율(11%)과 위치
패턴은 §2.1의 순회 아티팩트와 동일합니다. 즉 §2.1에서 `-`가 "손상"으로
보였던 것과 §2.2에서 `-`가 "가끔 맞는 값"으로 보이는 것은 **같은 아티팩트**
이며, 보고 부호는 참 부호와 무관합니다.

## 3. 추정 원인

사용 중인 디지털 셀(LABD-B3/K3) 프로토콜에서 무게값은
`[St 상태][X4: division 코드 + bit7 부호][X3 X2 X1: 크기]`의
**부호-크기(sign-magnitude) 분리 표현**입니다. 두 캡처를 종합하면:

- MCU가 **X4의 bit7(음수 플래그)을 판독하지 않거나 판독 결과를 버리고**,
  기본값 `+`로 6문자 변환을 수행하는 것으로 보입니다 (음수 참값이 89~94%
  `+`로 보고됨).
- 프레임당 1~2개(인접) 채널에 실리는 순회형 `-`는 참 부호가 아니라 주기적
  이벤트(틱 인터럽트, 다른 통신 처리 등)가 스캔/변환 루프와 간섭하며 만드는
  아티팩트입니다 (참값 양수인 채널에도 동일 비율로 실림).
- 크기(X3X2X1) 경로는 두 조건 모두 정확합니다.

## 4. 요청 사항

1. **(필수) 참 부호 판독·전달**: 셀 응답의 X4 bit7을 실제로 판독하여
   크기(X3X2X1)와 동일 수신 버퍼 스냅샷에서 원자적으로 조합해 주십시오.
   음수 값은 클램프/영점 복귀 없이 `-XXXXX`로 그대로 전달되어야 합니다.
   검증 기준은 §5 참조.
2. **(권장) St 상태 바이트 전달**: 셀이 보내는 St의 Stable(bit1)·에러
   비트들이 현재 6문자 변환에서 소거됩니다. 프로토콜 확장 여지가 있다면
   안정 플래그 전달을 검토해 주십시오 (상위 판정 시스템의 안정 구간 검출을
   하드웨어 신호로 대체 가능).
3. **(참고) 분해능 정합**: 센서 스펙이 division 1g / **분해능 5g**이므로,
   장기적으로 펌웨어 또는 셀 설정(division 레지스터, d=5 지원)에서 5g 단위
   보고로 정합하는 방안도 논의를 요청합니다.

## 5. 재현·검증 방법

에지 장비의 진단 스크립트로 수정 전/후를 동일 기준으로 비교할 수 있습니다:

```bash
python3 loadcell_diag.py run -o capture.jsonl --duration 60
```

- 수정 전: 섹션 [1]에서 채널당 sign-flips ~150회/664프레임, duty 0.88.
- 수정 후 합격 기준 ①: **전 채널 sign-flips = 0** (적재 정지 상태 60초).
- 수정 후 합격 기준 ②: 500g 추 영점 후 제거 상태에서 **duty ≈ 0.00**
  (−500이 지속 보고, `+` 혼입 없음). 부호 미전송 결함까지 고쳐졌는지는
  이 음수 영역 기준으로만 확인됩니다.

## 6. 엣지 임시 조치와 그 한계 (참고)

펌웨어 수정 전까지 IO-BOARD 파이썬 서비스 `get_loadcells()` 관문에
글리치 보정(미디언-of-3 + 부호 연속성 가드)을 적용했습니다
(`src/services/io_board/sanitizer.py`, `IO_BOARD__SANITIZE__*` 설정).
**양수 영역**에서는 실측 캡처 리플레이 기준 오염 샘플이 채널당 79→3개
(부팅 직후 0.3초분)로 복구됩니다.

단, **음수 영역은 엣지에서 복구가 원리적으로 불가능합니다** — 부호 정보가
와이어에 실리지 않으므로(§2.2) 어떤 필터도 참 부호를 알 수 없습니다.
현재는 "빈 선반 영점 → 측정값 상시 양수" 운영 전제로만 정합성이 유지되며,
재고가 실린 상태에서 영점이 잡히는 순간(정전 복구, `MC LZ` 오호출 등)
집기(−)가 반품(+)으로 뒤집혀 보일 수 있는 위험이 남습니다. 이 때문에
펌웨어 단 수정이 반드시 필요합니다.
